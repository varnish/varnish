# vmod/ — AGENTS.md

VMODs are dynamically loaded shared libraries that extend VCL with new functions and objects. Built-in VMODs live in this directory, as a flat list (not per-vmod subdirectories, aside from `vmod/tests/`).

Each VMOD consists of:
- `vmod_<name>.vcc` — interface definition; parsed by VCC to generate C bindings (see [lib/libvcc/AGENTS.md](../lib/libvcc/AGENTS.md))
- `vmod_<name>.c` — C implementation
- `vcc_<name>_if.c` / `vcc_<name>_if.h` — auto-generated by `lib/libvcc/vmodtool.py`; do not hand-edit
- `tests/<name>_*.vtc` — test cases (see [../bin/vinyltest/AGENTS.md](../bin/vinyltest/AGENTS.md) for the VTC DSL)

`.vcc` stanzas:
- `$Module name version "description"` — module declaration
- `$Function RETTYPE name(ARGTYPE arg, ...)` — exported function
- `$Object Name(...)` — object type (constructor)
- `$Method RETTYPE .method(...)` — method on an object
- `$Event func_name` — lifecycle hook (load/unload/warm/cold)
- `$ABI strict|vrt` — ABI compatibility mode

C implementation conventions:
- Function: `VCL_RETTYPE vmod_<name>_<func>(VRT_CTX, VCL_ARGTYPE arg, ...)`
- Object constructor: `void vmod_<name>__init(VRT_CTX, struct vmod_<name> **, const char *vcl_name, ...)`
- Object destructor: `void vmod_<name>__fini(struct vmod_<name> **)`
- First argument is always `VRT_CTX` (see below)

Built-in VMODs:
- `vmod_blob` — binary data encoding (base64, hex, URL)
- `vmod_cookie` — HTTP cookie parsing
- `vmod_debug` — debugging utilities
- `vmod_directors` — backend load balancing (round-robin, hash, shard, fallback, random)
- `vmod_h2` — HTTP/2 features
- `vmod_math` — mathematical functions. Unlike the others, both `vmod_math.vcc` and `vmod_math.c` are **generated at build time** from `vmod_math_spec.html` via `vmod_math_gen.py` — there are no static source files to hand-edit; edit the spec/generator instead.
- `vmod_proxy` — PROXY protocol
- `vmod_purge` — cache purging
- `vmod_std` — standard library (random, round, collect, strstr, etc.)
- `vmod_tls` — TLS inspection (JA3, SNI) (see [../bin/vinyld/tls/AGENTS.md](../bin/vinyld/tls/AGENTS.md))
- `vmod_unix` — Unix socket utilities
- `vmod_vtc` — test utilities

## `struct vrt_ctx` / `VRT_CTX`

Every VMOD function receives `const struct vrt_ctx *ctx` as its first argument (the `VRT_CTX` macro expands to this type, declared in `include/vrt.h`). It is the bridge between VCL and C.

Relevant fields (which are non-NULL depends on the VCL context):
- `ctx->req` — client-side request (`struct req *`, NULL on backend side)
- `ctx->bo` — backend fetch (`struct busyobj *`, NULL on client side)
- `ctx->sp` — session (`struct sess *`)
- `ctx->vcl` — active VCL program
- `ctx->vsl` — VSL log handle for this transaction
- `ctx->http_req`, `ctx->http_resp` — client request/response headers
- `ctx->http_bereq`, `ctx->http_beresp` — backend request/response headers

To signal a VCL runtime error from a VMOD: `VRT_fail(ctx, "message: %s", reason)`. This sets the error and causes `return(synth)` or `return(error)` depending on context.

## Create a new VMOD function

1. Add to `vmod_<name>.vcc`:
   ```
   $Function STRING my_func(STRING input, BOOL flag=0)
   ```
2. Implement in `vmod_<name>.c`:
   ```c
   VCL_STRING
   vmod_mymod_my_func(VRT_CTX, VCL_STRING input, VCL_BOOL flag)
   {
       CHECK_OBJ_NOTNULL(ctx, VRT_CTX_MAGIC);
       if (input == NULL)
           return (NULL);
       /* allocate result in workspace */
       return (WS_Printf(ctx->ws, "result: %s", input));
   }
   ```
3. Add a test in `vmod/tests/<name>_*.vtc`

## Bundling a new VMOD into core

Whether a new VMOD belongs in this directory (bundled with the core distribution) versus as an out-of-tree VMOD is governed by policy in `doc/sphinx/dev-guide/policy_vmods.rst` — in short: no new external dependencies, must pass `make distcheck`, and the author must commit to ongoing maintenance. Read that file before proposing a new built-in VMOD.
